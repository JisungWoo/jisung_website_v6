01 / Snowflake느리거나 결과가 잘못된 쿼리를 진단하는 방법+

실제 개선 경험

SQL과 데이터 처리 구조를 함께 개선했습니다.

실행 내역부터 확인합니다

설계용 뷰에 단순 SELECT를 실행해도 완료까지 2~3시간이 걸렸습니다. Snowflake Query History로 실행 내역을 확인하고, 여러 CTE와 서브쿼리, 수십 개의 조인이 얽힌 로직을 단계별로 살펴보며 오래 걸리는 부분을 좁혀 갔습니다.

SQL과 처리 구조를 함께 개선했습니다

필요한 데이터를 앞 단계에서 걸러낼 수 있도록 CTE와 WHERE 조건을 조정하고, SELECT * 대신 필요한 컬럼을 명시했습니다. 필요한 로직을 유지할 수 있는 경우에는 설계용 뷰 대신 데이터 모델이나 리포팅 뷰를 참조했습니다. 뷰와 스테이징 테이블을 추가하는 방안을 먼저 제안했고, 팀과 함께 중간 결과를 저장하는 구조로 변경했습니다.

단계가 늘어나는 대신 중간 결과를 저장합니다

변환 단계 사이에 테이블을 두면 중간 결과를 이후 단계에서 다시 사용할 수 있습니다. 저장 공간과 적재 작업이 추가되는 만큼, 데이터 아키텍트와 협의해 갱신 순서와 주기를 정했습니다. 적재 실패 시 재처리 방식은 이 사례에서 구체적으로 다루지 않습니다. CTE를 사용하는 것만으로 결과가 테이블에 저장되는 것은 아닙니다.

개선 후 전체 데이터 갱신은 약 30분에 완료됩니다. 변경 전후의 행 수를 비교하고 MINUS 쿼리로 결과의 차이를 확인했습니다. 코드의 처리 로직을 바꾼 뒤 검증할 때도 대기 시간이 줄었습니다. 실제 업무 경험을 바탕으로 기재한 결과이며, 기존 2~3시간은 SELECT 실행 시간이므로 전체 갱신 시간과 같은 조건으로 비교한 수치는 아닙니다.

조사 방법을 설명하는 간단한 예제

주문 하나에 품목 두 개가 연결되어 있습니다. 주문 컬럼만 조회하면 조인 결과가 중복으로 보입니다. 불필요한 조인을 제외하고 행 수를 비교해 보세요.

쿼리 구성

학습용 가상 예제입니다. 식별자와 데이터는 임의로 만들었으며 Honeywell 데이터가 아닙니다. 진단 방법을 보여주는 예제로, 실제 장애나 성능 측정 대상 쿼리를 재현한 것은 아닙니다.

SELECT o.order_id, o.status
FROM demo_orders o
LEFT JOIN demo_lines l
  ON o.order_id = l.order_id;

03 / Cortex매핑 대상별로 확인해야 할 범위+

프로토타입 / 사람의 검증 필요

뷰 하나만으로는 전체 흐름을 알 수 없습니다.

Cortex 프로토타입은 수백 개 컬럼의 정의와 매핑 초안을 작성합니다. 데이터 모델을 매핑할 때는 그 모델이 만들어지기까지의 로직을 확인해야 합니다. 리포팅 뷰를 매핑할 때는 모델 이후에 적용되는 변환 과정도 확인해야 합니다.

매핑 대상 선택
  1. 01스테이징 · 설계 로직
  2. 02팩트 테이블 · 데이터 모델선택한 대상
  3. 03데이터 마트 변환
  4. 04리포팅 뷰선택한 대상

모델 매핑 범위: 스테이징과 설계 로직부터 팩트 테이블·모델 계층까지 확인합니다.

프로젝트의 데이터 처리 단계를 간략히 나타낸 예시입니다. 실제 운영 구조를 그대로 재현한 것이 아니며, 회사 모델명·SQL·생성된 매핑 문서는 공개하지 않습니다.

수작업으로 4시간 이상

복잡한 모델 하나의 매핑 문서를 수작업으로 작성하는 데 걸린 시간입니다. 당시 업무 경험을 기준으로, 자동 초안 작성에는 몇 분이 걸렸습니다. 검토까지 포함한 전체 소요 시간은 아직 측정하지 않았습니다.

상급자에게 시연한 초기 프로토타입

상급자에게 시연했으며, 아직 다른 팀에서 사용하고 있지는 않습니다. 같은 조건에서 반복해 검증할 수 있는 정확도 평가 결과도 아직 없습니다.
